# ADR 00001: 再生と共有で単一Fileを共用し1タップ共有を維持する

- Status: accepted
- Date: 2026-08-11
- Supersedes: none
- Superseded by: none

## Context

完成動画の保存・共有では、URLや投稿文だけでなくMP4ファイルそのものを
iPhone・iPadの共有シートへ渡す。これにより、利用者は「ビデオを保存」
「ファイルに保存」や各共有先を選べる。完成後の共有操作は1回のタップで完了することを
プロダクト要件とする。

この導線は実機フィードバックに応じて変遷してきた。最初はダウンロード後の手動添付を
なくすためOS共有シートへMP4を直接渡した。その後、X風のボタンからOS共有シートが
開く分かりにくさを避けるため、X投稿と動画保存を一度分離した。現在は専用サービスに
見える導線を増やさず、保存・共有ボタン1本からOS標準の共有先を選ぶ方針である。

iOS系ブラウザの Web Share API には、次の制約と実機上の挙動がある。

- `navigator.share()` はタップによる一時的なユーザー操作権限の中で呼ぶ必要がある。
  クリックハンドラ内でMP4の `fetch()` と `Blob` 化を待ってから呼ぶと、権限を失って
  共有シートを開けないことがある
- 1バイトのダミーMP4に対する `navigator.canShare()` が `false` でも、実際のMP4は
  共有できることがある。アプリ内ブラウザには `canShare()` がなく
  `share()` は使えるものもあるため、`canShare()` を門番にできない
- 共有シートを閉じた後も `navigator.share()` のPromiseが完了しないことがある。
  Promiseの完了までボタンを無効にすると再操作できなくなる
- キャンセルや共有エラーを自動ダウンロードへ置き換えると、利用者が意図しない保存を
  開始してしまう

1回のタップでファイル付き共有を開くには、タップ前にMP4を `File` として準備する必要が
ある。以前は、動画要素が直接URLを読み込み・デコードするのと同時に、同じURLを共有用にも
全量取得して `File` として保持していた。

その後、iPhone Safariでページがときどき終了して「問題が繰り返し起きました」となり、
再読み込みで回復する事象が報告された。クラッシュログ、端末ごとのメモリ計測、再現する
動画サイズは取得できておらず、原因は確定していない。直接URLによる再生と共有用の全量取得が
重なる実装は、観測されたタブ終了と整合するメモリプレッシャーの有力な作業仮説である。
また、完成状態を離れても進行中の共有用取得を中断していなかったため、複数取得が重なる
余地もあった。

## Decision

ファイル共有を試行できる候補環境では、完成時にMP4を1回だけ取得して `File` を作り、
その同じ `File` を共有と動画再生の両方に使う。

1. iPhone・iPad・Androidで、`navigator.share`、`File`、`URL.createObjectURL` の
   存在を候補判定に使う。`navigator.canShare()` の有無や結果だけで共有不可にしない。
   MacなどのPCでは共有シートに保存先が表示されないことがあるため、Web Share APIが
   利用可能でも共有を使わず、明示的な「動画をダウンロード」ボタンで直接保存する
2. 完成時、動画要素には直接URLを設定せず、共有ボタンを「共有を準備中…」として無効にし、
   MP4を1回だけ取得する
3. 取得した `Blob` から共有用 `File` を作り、その `File` のobject URLを動画要素の唯一の
   sourceにする。準備完了後に共有ボタンを有効にする
4. 準備後の最初のタップでは、通信や非同期処理を先に挟まず、準備済み `File` と共有本文を
   `navigator.share()` へ渡す。共有本文には `#Soramimic` と現在のサイトのoriginを含める
5. 完成状態から離れるときは、取得を中断し、動画要素を停止してsourceを外してから
   object URLをrevokeし、`File` への参照を外す

合わせて次を不変条件とする。

- `navigator.share()` のPromiseを待つためにボタンを無効化しない
- `AbortError` はキャンセルとして何もしない。その他の共有エラーでは保存モードへ切り替え、
  次の明示タップでのみ直接ダウンロードする
- 共有用MP4の取得に失敗した場合は、動画要素を直接URL再生へ切り替える。自動ダウンロードは
  行わず、ボタンを明示的な直接保存モードにする
- 共有用MP4の取得が30秒以内に完了しない場合も取得を中断し、直接URL再生と直接保存へ
  切り替える。動画再生を共有準備の無期限な待機に巻き込まない
- object URLの読み込み・デコードが非同期に失敗した場合は、共有用 `File` は維持したまま、
  動画再生だけを直接URLへ切り替える。この例外時のみ二経路の保持を受け入れる
- Web Share API、`File`、object URLのいずれかがない環境では、動画を直接URLで再生し、
  最初のタップで動画URLを直接ダウンロードする

## Alternatives considered

- **準備と共有を2回の明示タップに分ける**: 通常表示時の先行取得を避けられるが、完成後の
  1タップ共有というプロダクト要件を損なうため採用しない
- **動画は直接URL、共有用Fileは別途先行取得する**: 1タップ共有はできるが、同じMP4を
  二経路で同時に読み込む構成が今回の事象と整合するため採用しない
- **1回のタップ内で取得後に共有する**: iOSの一時的なユーザー操作権限を失い、共有シートを
  開けないことがあるため採用しない
- **iOSでは常に動画URLを直接ダウンロードする**: 写真・ファイル・各アプリを選べる
  ファイル付き共有を失うため採用しない
- **PCでもWeb Share APIがあれば共有シートを開く**: Macでは保存先が見つけにくく、
  動画プレイヤーのメニューから別途ダウンロードする必要があるように見えるため採用しない
- **ダミーファイルを `canShare()` へ渡して事前判定する**: 実ファイルを共有できる端末でも
  誤って不可と判定するため採用しない
- **Service Worker、Cache API、OPFSへ動画を退避する**: `File` 生成時のメモリ挙動や
  iOSの共有互換性を保証できず、quota・cleanup・対応差も増えるため現時点では採用しない

## Consequences

- 準備完了後は、最初のタップから動画ファイル付き共有シートを開ける
- 直接URL再生と共有用取得を同時に行わず、圧縮MP4は1つの `File` を再生と共有で共用する
- 動画再生もMP4全体の取得完了まで始められない。二重読み込みを避ける代わりに、
  direct streamingよりtime-to-first-playが遅くなる。30秒で準備できなければ直接再生へ戻る
- `File` 全体の保持、動画のデコード用メモリ、共有先への転送時にブラウザ内部で行われる
  可能性のあるコピーは残る。また、`Blob` から `File` を作る際の内部ストレージ共有も
  ブラウザ実装依存である。したがって、この判断がメモリ使用量を必ず減らすとは断定しない
- iPhone・iPad・Androidでは候補APIの有無で共有を選び、PCでは直接ダウンロードを選ぶ。
  iPadのデスクトップ表示はタッチポイント数も使ってiPadとして扱う
- 実機での再発有無を継続して確認する。再発する場合はクラッシュログ、端末、動画サイズ、
  共有準備中か再生中かを記録し、直接URL保存や動画サイズの上限を別ADRで検討する
- 回帰テストでは、完成時の取得が1回であること、直接動画URLを同時設定しないこと、
  同じ `File` をobject URLと共有payloadへ渡すこと、最初のタップで追加通信なしに共有する
  こと、状態離脱時の取得中断・source解除・URL破棄を固定する
